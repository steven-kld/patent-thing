## 1. Экономическая рамка (принята 2026-09-10, назначена, не выведена)

```
структура        ставка на «есть §103» или пас; пас = $0
выигрыш          +$10        верная ставка
проигрыш         −$80        неверная ставка
L                8
порог безубыточности   p* = L/(L+1) = 8/9 = 0,8889

час работы       $50
день             3 часа = $150
гипотеза         10 дней = 30 часов = $1 500
порог окупаемости ×2   →   $3 000

ПРАВИЛО РЕШЕНИЯ: суммарный EV на тесте ≥ $3 000
```

Следствия, выведенные из рамки (не назначенные):

```
EV(ставка при p) = 90p − 80
пол по числу ставок = $3 000 / $10 = 300 ставок = 2,8% теста
потолок (идеальная модель) = 8 219 × $10 = $82 190;  планка = 3,65% потолка

p      EV/ставку   нужно ставок   доля теста (при N=10 814)
0,90     $1,0        3 000          27,7%
0,92     $2,8        1 071           9,9%
0,95     $5,5          545           5,0%
0,97     $7,3          411           3,8%
1,00    $10,0          300           2,8%
```

**Порог ставки не назначается** — выбирается на valid по максимуму суммарного EV.
Покрытие выпадает из правила само.

**Минимальный носитель кластера** — не новый параметр: `min_child_samples = 50`
в LightGBM и `C` в логрег L2 играют эту роль.

Ограничение, связывающее рамку с данными:
```
требуется точность метки  a ≥ p* = 0,8889     ← измерено, см. §6
```

Известные оговорки:
- `L = 8` **назначен** (учебная задача), не выведен из рынка;
- valid используется **четырежды**: ранняя остановка, гиперпараметр, калибратор,
  выбор порога ставки. Оценки на valid оптимистичны сильнее, чем в r3;
- форма выплат (short-volatility: часто по чуть-чуть, редко много) **обратна**
  форме аукциона доменов (убыток ограничен ставкой, выигрыш длиннохвостый).

## 3. Механика тарификации BigQuery — проверено, не предположено

- `WHERE` **удорожает** ровно на стоимость столбца фильтра. Партиционирования и
  кластеризации у `publications` нет. Четыре сверки сошлись **до байта**:

```
D11 = D3 + country_code        123 180 757 785 = 123 180 757 785
D12 = D3 + publication_date    123 862 431 701 = 123 862 431 701
D13 = сумма 7 столбцов         132 333 654 599 = 132 333 654 599
D15 = D13 + abstract[0].text   339 424 177 996 = 339 424 177 996
```

- **`LIMIT` не влияет.** `COUNT(*)` = 0 байт. Размер когорты — не рычаг.
- **Прунинг подполей:** на **повторяющихся массивах** не работает
  (`claims_localized` → 0,08%, `abstract_localized` → 0,58%);
  на **обычных структурах** работает отлично
  (`sections` 86,93 ГиБ → `sections.summaryText` 0,02 ГиБ).
- **`TABLESAMPLE SYSTEM` снижает байты почти линейно** — рычага не было ни в r3,
  ни в прошлых сессиях:

```
publications, claims[0].text:   0,01% → 8 854 485    0,1% → 123 962 795    1% → 1 248 482 436
office_actions_text, bodyText:  0,1%  → 161 738 097  1%   → 1 940 857 169
```

Блочная выборка, не строковая: для оценок частот годится, для отбора конкретных
строк — нет.

### Ключи — сходятся


### Типы преемственности — важная поправка

```
CON, DIV, CIP    настоящие продолжения      → исключать
PRO              приоритет от provisional   → НЕ продолжение, первичная подача
NST              национальная фаза PCT      → НЕ продолжение
```

Наивный фильтр «есть родитель» убрал бы **47,0%**; правильный `CON|DIV|CIP` —
**22,7%**. Бриф r3 ждал 25–35%; факт ниже вилки.

```

CON,PRO 1 028   CIP,PRO 250   CIP 250   DIV 201
```

### Диаграмма потока

```

2015 H1 (train)     14 126        268       3 206      10 920     9 825     9 133    69
```

## 6. Точность метки — измерено в правильном порядке

`L = 8` назначен → `p* = 0,8889` выведен → **потом** измерено. Правило существовало
до числа; загрязнения нет.

Метод: две независимые регулярки по `bodyText`, построенные после чтения
документов глазами. Выборка `TABLESAMPLE 5%`, TC 2100, 2015, первые OA по существу.

```
B2  (?is)rejected\s+under\b.{0,60}?103
E   (?i)Claim\s+Rejections\s*[-–]\s*35\s*USC\s*§?\s*103
```

Валидация на 30 прочитанных документах:
```
A  наивная «103»                 согласие 76,7%   ← мусор, ловит шаблон
B2 «rejected under … 103»                96,7%
E  заголовок раздела                     96,7%
C2 «claims … are rejected under»         93,3%    ← теряет иную формулировку
```

Единственное расхождение B2/E с флагом — заявка `14026987`, прочитана глазами:
```
«Claims 3, 8, 11, 16 and 19 are rejected under pre-AIA 35 U.S.C. §103(a)
 as being unpatentable over Lawton in view of Jones et al.»
```
Отказ есть, `rejection_103 = '0'` — **ошибка OCE**, подтверждена.

**Критерий, без которого регулярка не строится:**
```
ШАБЛОН, не отказ:  «The following is a quotation of pre-AIA 35 U.S.C. 103(a)…»
                   + факторы Graham v. John Deere
ОТКАЗ:             «Claims N are rejected under 35 U.S.C. §103(a) as being
                    unpatentable over X in view of Y»
```

### Результат на 1 292 строках

```
флаг=0:  всего 314   обе регулярки нашли §103 →  8    регулярки спорят →  3
флаг=1:  всего 978   обе НЕ нашли §103        →  0    регулярки спорят → 35

ложноотрицательных среди флага 0:  2,55%   95% ДИ [1,30% ; 4,95%]
ложноположительных среди флага 1:  0,00%   95% ДИ [0,00% ; 0,39%]

консервативно   8/1 292 = 0,62%   ДИ [0,31% ; 1,22%]
пессимистично  46/1 292 = 3,56%   ДИ [2,68% ; 4,72%]

потолок точности  a ∈ [0,953 ; 0,994]     требуется 0,8889  →  ПРОХОДИТ
```

Истина ближе к нижней границе: 33 из 38 спорных — «B2 нашла, E нет», то есть
отказ есть, а заголовок оформлен иначе.

**Ошибки односторонние: метка прячет отказы, а не выдумывает.**

Экономическая цена шума:
```
доля скрытых среди истинно-103:  8/(943+8) = 0,84%
потеря на ставку = 0,0084 × ($10 + $80) = $0,76
EV при p=0,95:  $5,50 → $4,74      ≈ 14% прибыли
```

Истинная базовая ставка ≈ **0,766** вместо измеренных 0,7596.

`rejection_fp_mismatch` как детектор **слаб**: ловит 3 из 8 ошибок (37,5%),
точность 3 из 27 срабатываний (11%). Выбрасывать строки по нему нельзя.

**Принято:** чистка делается **до** прогона, а не после. Степень свободы
«не хватило → почистили → хватило» закрыта.

Оговорка: восемь подтверждённых ошибок глазами не читались (кроме `14026987`
из другой выборки). Регулярка принята за истину на основании 30 документов.

## 8. План выгрузки

**Материализовать свидетельства, а не решения.** Одна строка на кандидата,
каждый фильтр — колонка-флаг, ни одного `WHERE`:

```
is_continuation · has_apub · pub_before_oa · fp103_present · fp_mismatch · rn
```

Тогда чистка и фильтрация стоят ноль и обратимы. Ошибка `PRO`/`NST` при таком
устройстве стоила бы одной строки SQL вместо повторной выгрузки.

```
Этап A  ~12,2 ГиБ   когорта, ключи, даты, преемственность, сигнал чистки,
                    publication_date из снапшота (чинит дыру 2016)
Этап B   75,7 ГиБ   текст формул, снапшот, без абстракта
                    добавляется ТОЛЬКО когда набор строк окончателен
```

Джойн по ID **не удешевляет** текст — столбец сканируется целиком независимо от
числа подставленных ключей. Отложить текст = страховка, а не скидка.

Опция с ценником: материализовать `bodyText` для когорты — **186 ГиБ**
(`TABLESAMPLE` не поможет, нужны конкретные строки). Сделало бы всю дальнейшую
работу с меткой бесплатной. Пока `fp103` за 5,32 ГиБ достаточен.

## 10. Что было сделано в неправильном порядке

Записано, чтобы не повторить.

1. **Запись №1 предрегистрировала весь протокол** до выполнения хоть одного гейта.
   Абсолютные пороги назначены поверх неизмеренной выполнимости.
2. **Гейт G4 закрыт на не той популяции.** Мерил долю классов на 27 312 строках
   сырой когорты 2015; метрика живёт на ~10 814 строках теста после фильтров.
   `min(p,1−p)·N/K` при правильном `N` даёт **38,8** против порога 50.
3. **Порог 50 на страту теперь загрязнён** — число 38,8 увидено.
   Загрязнены также: доля классов 0,7596, размеры сплитов.
   Чист: `ΔAUC > 0,02` (ничего измеренного его не касалось).

Правильная последовательность:
```
0. паспорт источника      происхождение, vintage, покрытие, детерминизм
1. точность метки         потолок; критерий остановки
2. сборка когорты         воспроизводимая, диаграмма потока, потери
3. выполнимость метрик    относительные ограничения на фактических N и K
4. ПРЕДРЕГИСТРАЦИЯ        абсолютные пороги — только теперь
5. обучение
6. однократное раскрытие теста
```

Три недостающих правила стенда:
1. определение когорты — чистая функция от данных (два прогона = одно число);
2. каждый гейт записывает популяцию, на которой посчитан;
3. `data_ref` содержит vintage источника, а не только имя таблицы.

```
   30 док.     ПРОВЕРКА ИНСТРУМЕНТА      регулярка B2 против чтения
```

Изначально «регулярка против правды» имела `n = 1`: прочитан был только
`14026987`. Остальные 29 сверялись с флагом OCE, то есть с тем же, что и

```
B2 против чтения        30 / 30

```

Флаг=0 (15 док.): у четырнадцати заголовка `Claim Rejections - 35 USC § 103` нет
вовсе. У `14026987` есть, и есть предложение об отказе.

Флаг=1 (15 док.): у всех пятнадцати заголовок §103 присутствует. Два случая

```
13772518   «Claim1, 7, 8, 9 are rejected under pre-AIA 35 U.S.C. 103(a)…»
             — «Claim1» без пробела, \b не срабатывает
14487117   «Claims 1-25 rejected under 35 U.S.C. 103…»
             — «rejected» без «are»
```

Обе формулировки ломали строгий вариант `C2`. **Свободная `B2` правильнее
строгой**, и это не небрежность, а свойство исходного текста.

### Регулярку нельзя проверить другой регуляркой

Две попытки автоматизировать сверку дали два разных бага:

1. класс `[^.]` не проходит через точки в «U.S.C.» — окно обрывается, «Claims»
   и «rejected» в него не попадают;
2. окно ±180 символов ловит соседний заголовок `Claim Rejections - 35 USC § 102`
   из служебного абзаца «AIA 35 U.S.C. 102 and 103», давая ложные срабатывания
   на шести документах подряд.

Проверка инструмента — это чтение. Автоматизация проверки воспроизводит те же
классы ошибок, ради поиска которых она затевается.

## 18. Исправление оценки точности метки

Опубликованная ранее «пессимистичная» граница **3,56% построена неверно** и
отозвана.

`46 = 8 + 38 спорных`, где среди спорных 35 строк с флагом 1 и сработавшим
инструментом. То есть строки, где инструмент **подтверждает** метку, были
засчитаны в кандидаты на её ошибку. Величина `3,56%` меряет расхождение
инструментов между собой, а не расхождение метки с текстом.

Правильная конструкция — кандидат в ошибки есть строка, где метку **опровергают**:

```
флаг=0  оба инструмента подтверждают метку     303
флаг=0  инструменты спорят                       3   ← весь зазор 8→11
флаг=0  оба ОПРОВЕРГАЮТ                          8
флаг=1  оба подтверждают                       943
флаг=1  один подтверждает, второй молчит        35
флаг=1  оба ОПРОВЕРГАЮТ                          0

ошибка метки   8/1292 = 0,62%  ДИ [0,31% ; 1,22%]
              11/1292 = 0,85%  ДИ [0,48% ; 1,52%]
точность       a ∈ [0,985 ; 0,994]        было ошибочно [0,953 ; 0,994]
```

### Снятый довод

Утверждение «случайные склейки B2 завышают оценку, значит 0,62% — верхняя
граница» **неверно**. «Подтверждённая ошибка» требует срабатывания **обоих**
инструментов; склейка вида `rejected under 101. Claim Rejections - 35 USC § 103`
содержит заголовок, значит `E` сработает тоже. Но наличие заголовка само есть
свидетельство существования раздела §103 — на 30 прочитанных `E` срабатывала
ровно на 16 документах с реальным отказом, 16/16. Восемь «подтверждённых ошибок»
скорее настоящие, чем артефакты.

### Инструмент ужесточён до B4

```
B2 = (?is)rejected\s+under\b.{0,60}?103                    30/30, 2 склейки
B4 = (?is)rejected\s+under\s+(?:pre-?AIA\s+)?
          35\s*U\.?\s*S\.?\s*C\.?\s*§?\s*103               30/30, 0 склеек
```

На документах 13854203 и 13978729, где B2 склеивала отказ по 101 с заголовком
§103, B4 находит только настоящие предложения об отказе (7 и 1).

### Границы знания и принятый риск

```

коррелированная ошибка    ≤ 11,35%    только чтение 30 документов, 0 промахов
конфигурация B2≠E                     в валидационной выборке 0 раз
```

плюс 11 опровергающих плюс 37 спорных), 9,3 ГиБ + 6–18 часов чтения = $300–900.

