## Вход: решения автора до всякого счёта (2026-10-04)

Ни одна модель не обучена, ни одно разведочное число не получено. Все
решения ниже приняты до появления любой величины, зависящей от `y`.

### Энкодер

```
модель        Nomic Embed v1.5, 137M, размерность 768, окно 8192
дообучение    нет
префикс       classification: — на всех восьми вариантах
перебор       ни модель, ни префикс на разведке не перебираются
```

Признак отбора объявлен в Protocol (`selection._проза_автор_энкодер`, план
разведки «энкодер»): длинное окно, открытые веса, без дообучения, один на все
восемь. Сужение до четырёх семейств (BGE-M3, GTE-en-v1.5, Nomic v1.5,
Jina v2/v3) сделано в сессии 2026-10-03, в артефакт не попало.

Слова автора:

> «формально они все нам подходят, но мы берем только 768, первая отпадает.
> из остальных надо выбрать ту, которая будет дешевле»

Замер цены (токенизатор × скорость на целевой GPU) автор отменил:

> «знаешь, забей. Nomic Embed v1.5 137M берем»

То есть выбор между тремя моделями 768 (GTE-en-v1.5 base, Nomic v1.5,
Jina v2 base) сделан назначением, не измерением.

Префикс. Сначала назначен `clustering:`, затем изменён на `classification:`
после справки ассистента о значении префиксов в документации Nomic («класс»
там — метка, которую учится предсказывать классификатор, у нас — 103 / не 103).
Изменение до любых чисел и не по данным. Слова автора:

> «тогда у нас абсолютно точно классификейшн. кластеризация это задача по
> мелкой нарезке, а у нас бинарный ответ. я меняю свое решение из-за
> комментария по документации, выбираем классификейшн»

Версия весов — коммиты Hugging Face, сняты API 2026-10-04. Модель грузит код
из второго репозитория (`trust_remote_code`), поэтому закрепляются оба:

```
веса    nomic-ai/nomic-embed-text-v1.5   e9b6763023c676ca8431644204f50c2b100d9aab   (2026-04-07)
код     nomic-ai/nomic-bert-2048         7710840340a098cfb869c4f65e87cf2b1b70caca   (2025-04-29)
```

Грузить с `revision=` на эти хеши, не `main`.

Библиотеки: закреплённый код `nomic-bert-2048` несовместим с transformers 5.x
(`get_extended_attention_mask` удалён) — стоит `transformers 4.57.6`.
Локально `torch 2.14.1+cpu`; на GPU-машине будет CUDA-сборка — побитового
совпадения векторов между CPU и GPU не ожидается, детерминизм проверяется
внутри одной машины. Проверка загрузки: 136 731 648 параметров, выход 768.

Факт из `config.json` той же ревизии: `max_trained_positions = 2048`,
`n_positions = 8192`, `rotary_scaling_factor = None`. Модель обучена на
кусках до 2048 токенов; окно 8192 достигается растяжением позиций, которое
по умолчанию выключено. Касается выбора размера куска (ось автора).

### Нарезка

Решения автора 2026-10-04, до любых чисел, зависящих от `y`. Все замеры ниже —
на признаках train+valid (N = 23 560), `confirm_2016H2` не читался.

```
элементы    ta = title + abstract, целиком, никогда не режется
            c  = claims, режется внутри себя
            d  = description, режется внутри себя
            куски не пересекают границу полей
варианты    tacd = ta + c₁…cₙ + d₁…dₘ;  tac = ta + c₁…cₙ;  c;  d
            собираются из одних векторов кусков
нарезки     крупная: кусок ≤ 2048 токенов (тело 2044)
            мелкая:  кусок ≤ 1000 токенов (тело 996)
служебные   4 токена на кусок: префикс classification: + маркеры
нахлёст     250 токенов в обеих нарезках, только внутри c и d
            мелкая: 25,1% тела, шаг 746, токенов ×1,34
            крупная: 12,2% тела, шаг 1794, токенов ×1,14
хранится    вектор каждого куска (768); сведение и усечение — на разведке
```

История решения, в порядке принятия:

1. «кусок не более 2048» — верхняя граница, по `max_trained_positions`.
2. «мы создаем из всего единый документ» — склейка полей варианта в один
   текст. Отменено следующим пунктом.
3. «это абсолютно разные по сути вещи, резать их будет абсолютно глупо. я бы
   всегда делал элемент ta, потом элемент c нарезанный на части и потом
   элемент d на части, так, чтобы ta не перемешивались с c,d»
4. «мелкая нарезка будет по 1000 токенов»
5. Нахлёст: сначала «20% от тела», затем «от 20 до 40 в зависимости от
   размера заявки», затем «мы нарежем так, чтобы попадало именно равное число
   токенов, а не %», и итог: «мне хочется начать с 250 токенов. 400 выглядят
   плохо учитывая окна по 1000». Сомнение автора: «меня очень сильно смущают
   повторы».

Замеры, на которых это принималось (токенизатор Nomic той же ревизии):

```

tac (с префиксом)      1 372  2 225 3 829 10 284    13,9%

единица               медиана  p90   p99   целиком ≤ 250
пункт claims, все         50   140   285   98,4%   (N 436 879; не разобрано 958 заявок)
  независимые            133   235   402   92,3%
  зависимые               44    97   202   99,5%
абзац d, ≥20 токенов      92   222   407   93,2%   (выборка 2 000 заявок, seed 14)
```

Правило покрытия: единица короче нахлёста целиком лежит хотя бы в одном куске.

**Объявлено до разведки (автор):** после обучения и выбора победителя на
разведке для него будет перебран нахлёст: «потом мы на этом все обучим,
появится победитель на валиде и потом для валида попробуем разный нахлест».
Нахлёста нет в `selection.space` — для F8 ось невидима (ревизия 26, дефект 10).

**Ось «нахлёст» — объявление (E6), решение автора 2026-10-04:**

```
значения    250 — для всех вариантов в первом проходе
            400 — только для победителя первого прохода
правило     ЗАМЕНЕНО (см. «Правило отбора» ниже): было argmax EV на
            scout_2015H2; автор свёл все оси к одному правилу — наименьшее
            число ставок, при котором ci_low пересекает 1650
всего       два значения; третье не пробуется
```

Слова автора: «250 и потом 400 только для победителя. выбираем ту же цель».
Место объявления — этот черновик (автор: «черновик билд»), а не Protocol.
Доказательство, что объявлено до разведки, — коммит этого файла автором

### Решение автора по братским заявкам (2026-10-04, до разведки)

```
сходство   cos векторов ta ≥ 0,95 — братья
обучение   заявки train, у которых есть брат, исключаются
ставки     заявка верхушки, у которой есть брат (в датасете, в верхушке
           или вне её), пасуется всегда; ни на кого из группы не ставим
```

Слова автора: «при 0.95 исключать из обучения, теряем крохи. по ta, тексты
скорее всего не будут братскими. ни ставим ни на кого. ... на тесте мы получим
все тексты, проставим им оценки, потом возьмем верхушку и поставим на нее.
если в верхушке есть братья по ta (то есть пересекаются или с датасетом, или
между собой в верхушке, или один брат в верхушке, а другой нет) - всегда пасуем».

Исключение — шаг замороженного конвейера (шаг 30), применяется к ящику один раз
при вскрытии; на признаках ящика до шага 31 не вычисляется. На разведке
работает так же (репетиция, E19).

Обучение — изменено автором: братья НЕ исключаются. «мы обучим на всех, даже
братьев, тк на обучении это мало скажется». Прежняя версия («при 0.95
исключать из обучения») отменена до любых чисел.

Момент предсказания для этого правила — конец окна, а не дата первого действия
каждой заявки: братья ищутся среди всех заявок train, обеих разведок и самого
ящика. Слова автора: «наша штука изначально задумана не по времени, а полугодие
разом. это похоже на "один день разом" на более частых событиях, потому что я
хочу прийти на рынок, увидеть все помидоры и купить только лучшие 10 помидор.
мб это не всегда в жизни сработает, но в данном дизайне эксперимента это
возможно». Брат с более поздней датой в том же окне — не утечка в этом
определении; в реальной работе по дням правило исполнялось бы не буквально.

На разведке (scout_2015H2): «датасет» — train и сама разведка; признаки ящика
до шага 31 не используются.

### Правило отбора — одно на все оси (2026-10-04, до разведки)

Оси: 8 вариантов, нахлёст (250 → 400 для победителя), размерность 256/512/768,
сведение кусков. Победитель — конфигурация, у которой ci_low(EV) на
scout_2015H2 впервые достигает 1650 при наименьшем числе ставок (заявки по
убыванию уверенности, братья — пас). При ничьей — меньшая размерность.
Слова автора: «победитель это тот, кто смог наименьшим числом ставок набрать
1650»; «при ничьей выбираем то, где ниже размерность»; «одно правило для всей
оси это верно». Заменяет selection.objective = argmax EV — уходит в новую
редакцию Protocol.

Сведение: перебираются оба (максимум и среднее), как в плане разведки. Ничья
разрешается по порядку: 1) меньшая размерность; 2) при той же размерности —
среднее. Слова автора: «я хочу взять среднее, а не максимум» — «только для ничьей».
